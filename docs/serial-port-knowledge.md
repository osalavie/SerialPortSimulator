# 串口通信知识文档

## 1. 文档范围

本文说明 RS-232/TTL 串口、Windows COM 端口、USB 虚拟串口以及本项目虚拟串口模拟器的基础概念、工作原理、数据收发流程和缓存策略。

串口通信可以从四个层次理解：

```text
业务协议层：请求、响应、帧头、长度、校验、CRLF
应用接口层：COM 端口、SerialPort、Read/Write、事件
串口驱动层：配置管理、读写队列、缓存、超时、流控
物理/传输层：UART、RS-232/TTL、USB CDC、虚拟设备
```

## 2. 基础概念

### 2.1 串行通信

串行通信把数据按位在一根或少量信号线上依次传输。串口通常使用两路独立数据线：

- `TXD`：发送数据。
- `RXD`：接收数据。
- `GND`：信号地，是电平判断的参考。

全双工串口可以同时发送和接收，因为 TXD 和 RXD 相互独立。

### 2.2 UART

UART（Universal Asynchronous Receiver/Transmitter）是常见的异步串行控制器。它负责：

- 添加起始位和停止位。
- 串行化发送数据。
- 采样并还原接收数据。
- 检测帧错误、校验错误和接收溢出。

“异步”表示收发双方没有共享时钟线，而是分别使用自己的时钟，通过约定的波特率和帧格式同步每个字符。

### 2.3 RS-232、TTL 和 USB 虚拟串口

| 类型 | 电平/传输方式 | 特点 |
|---|---|---|
| TTL UART | 通常 3.3 V 或 5 V | 常见于 MCU 板级通信 |
| RS-232 | 正负电压 | 抗干扰能力较强，传统 DB9 接口 |
| USB CDC/VCP | USB 数据包 | PC 上表现为 COM 端口，不一定有真实 UART 时序 |
| 蓝牙 SPP | 蓝牙协议栈 | PC 上通过系统创建 COM 端口 |
| 软件虚拟串口 | 驱动内部缓冲 | 由驱动决定读写、事件和缓存行为 |

RS-232 的逻辑电平和 TTL 不同，不能直接连接。TTL 空闲状态通常为高电平；RS-232 的空闲 Mark 状态通常为负电压，逻辑 `1` 和逻辑 `0` 使用相反极性。

### 2.4 COM 端口

COM 端口是 Windows 对串行设备的抽象名称，例如 `COM3`。应用程序通过 `CreateFile("\\\\.\\COM3")` 打开设备，然后使用：

- `ReadFile` / `WriteFile`：读取和写入字节。
- `GetCommState` / `SetCommState`：获取和设置串口参数。
- `SetCommTimeouts`：设置读取超时。
- `PurgeComm`：清空接收或发送队列。
- `WaitCommEvent`：等待接收数据、线路状态变化等事件。

.NET 的 `System.IO.Ports.SerialPort` 是对这些 Win32 API 的封装。

### 2.5 DTE 和 DCE

- DTE（Data Terminal Equipment）：终端设备，例如电脑。
- DCE（Data Circuit-terminating Equipment）：通信设备，例如调制解调器。

传统交叉连接时，一方 TXD 连接到另一方 RXD。现代 USB 转串口设备通常已经完成内部交叉。

### 2.6 常见控制线

| 信号 | 常见作用 |
|---|---|
| `DTR` | 数据终端就绪，常用于表示终端已打开或复位外设 |
| `DSR` | 数据装置就绪 |
| `RTS` | 请求发送，也常用于硬件流控 |
| `CTS` | 清除发送，表示对方允许发送 |
| `DCD` | 载波检测 |
| `RI` | 振铃指示 |

很多设备只用 TXD、RXD 和 GND，控制线可以不连接。

## 3. 串口参数

### 3.1 波特率

波特率表示每秒传输的码元数量。UART 使用二进制码元时，波特率通常等于每秒位数，即 bps。

常见波特率：

```text
1200, 2400, 4800, 9600, 19200, 38400, 57600,
115200, 230400, 460800, 921600
```

真实串口双方必须使用兼容的波特率，否则会采样错误，表现为乱码、帧错误或无法通信。

### 3.2 数据位

一个 UART 字符通常包含 5、6、7 或 8 个数据位。现代设备最常用 8 位。

### 3.3 校验位

| 校验 | 规则 | 能力 |
|---|---|---|
| None | 不添加校验位 | 无检测 |
| Odd | 数据位和奇校验位中 `1` 的总数为奇数 | 检测奇数个位错误 |
| Even | 数据位和偶校验位中 `1` 的总数为偶数 | 检测奇数个位错误 |
| Mark | 校验位固定为 1 | 特定设备使用 |
| Space | 校验位固定为 0 | 特定设备使用 |

奇偶校验不能纠正错误，也不能可靠检测偶数个位同时出错。重要业务协议通常还需要 CRC、校验和或消息认证。

### 3.4 停止位

停止位表示一个字符结束，常见为 1、1.5 或 2 位。Windows 串口配置中，1.5 停止位通常只适用于 5 数据位。

### 3.5 串口格式简写

`9600 8N1` 表示：

- 波特率 9600。
- 8 数据位。
- 无校验（None）。
- 1 停止位。

### 3.6 帧位数和吞吐量

一个 8N1 字符包含：

```text
1 起始位 + 8 数据位 + 0 校验位 + 1 停止位 = 10 位
```

理论字节速率：

```text
字节/秒 ≈ 波特率 ÷ 每字符位数
```

| 波特率 | 8N1 理论字节率 |
|---:|---:|
| 9600 | 960 字节/秒 |
| 19200 | 1920 字节/秒 |
| 57600 | 5760 字节/秒 |
| 115200 | 11520 字节/秒 |
| 921600 | 92160 字节/秒 |

实际吞吐还要扣除协议帧、校验、设备处理延迟、流控暂停和操作系统调度开销。

## 4. UART 工作原理

### 4.1 字符帧

典型 8N1 UART 字符帧：

```text
空闲(1)  起始(0)  D0 D1 D2 D3 D4 D5 D6 D7  停止(1)  空闲(1)
```

数据位通常低位先发送。接收方检测到起始位边沿后，在每一位的中间位置采样，以降低边沿抖动的影响。

### 4.2 常见线路错误

| 错误 | 含义 |
|---|---|
| Framing Error | 停止位位置不是期望电平，帧结构错误 |
| Parity Error | 校验位与数据不匹配 |
| Overrun Error | 新数据到达时旧数据尚未取走 |
| Break | 线路长时间保持逻辑 0 |

### 4.3 流控

硬件流控使用 RTS/CTS：

```text
接收方缓冲区接近满 → 撤销 CTS → 发送方暂停发送
接收方缓冲区恢复 → 拉高 CTS → 发送方继续发送
```

软件流控使用特殊字符：

- `XON`：允许继续发送。
- `XOFF`：要求暂停发送。

软件流控不适合未经转义的二进制协议，因为数据内容可能与 XON/XOFF 字符冲突。

## 5. 数据发送流程

真实串口发送路径：

```text
业务程序生成字节
→ SerialPort.Write / WriteFile
→ Windows 串口 API
→ 串口驱动的发送队列
→ UART/USB 发送引擎
→ TXD 或 USB IN 数据包
→ 接收设备
```

调用 `Write` 返回通常只表示数据已被驱动接受，不一定表示对方已经收到，也不代表已到达终端设备。

发送时可能发生：

- 驱动发送队列已满，写操作阻塞或失败。
- 流控要求暂停。
- 设备拔出导致写失败。
- USB 传输延迟导致短时间积压。

## 6. 数据接收流程

真实串口接收路径：

```text
设备发送
→ RXD / USB OUT
→ UART 或 USB 接收状态机
→ 串口驱动接收队列
→ 业务程序 Read
→ 应用层帧解析
```

接收事件流程：

```text
驱动收到字节
→ 触发 RXCHAR 等待事件
→ Windows 完成 WaitCommEvent
→ SerialPort 触发 DataReceived
→ 业务程序读取 BytesToRead
→ Read 将数据复制到应用缓冲区
```

`DataReceived` 只是“有数据可读”的通知，不保证：

- 一次事件对应一个完整协议报文。
- 一次 `Read` 读取所有字节。
- 一个 UTF-8 字符不会跨读取边界。
- 消息边界与串口读取边界一致。

业务协议必须自行定义分帧，例如 CRLF、长度字段、固定长度、帧头帧尾或转义规则。

## 7. 缓冲区和缓存策略

### 7.1 多层缓存

串口数据从设备到业务程序可能经过多层缓存：

```text
硬件 FIFO
→ USB/UART 驱动缓冲
→ Windows 串口队列
→ 业务程序内部缓冲
```

每一层容量都由硬件或软件实现决定，没有统一标准。

### 7.2 环形缓冲区

环形缓冲区使用固定内存和头尾指针循环复用：

```text
[ 未读数据 ][ 空闲空间 ]
            ↑头       ↑尾
```

它适合持续字节流，但必须处理：

- 可选空间不足。
- 可读数据长度。
- 写入跨越缓冲区尾部。
- 读取跨越缓冲区尾部。
- 生产者与消费者并发。

常见策略：

| 策略 | 空间不足时行为 |
|---|---|
| 阻塞生产者 | 等待消费者读取 |
| 丢弃新数据 | 保护旧数据，但产生丢失 |
| 覆盖旧数据 | 保护新数据，但破坏旧消息 |
| 返回溢出错误 | 明确告知上层写入失败 |
| 流控暂停 | 通过 CTS/XOFF 阻止发送方继续发送 |

### 7.3 首次读取出现一批旧数据

如果模拟器或发送端在业务程序打开 COM 前已经发送数据，这些数据可能仍在驱动接收队列中：

```text
驱动缓存了 4 条旧消息
→ 业务程序打开 COM
→ 第一次 Read 一次取出 80 字节
```

这不是重复接收，而是积压数据被一次性读出。后续消息按发送间隔陆续到达时，会形成后续批次。

### 7.4 真实串口无程序读取时

真实串口是否能缓存数据取决于端口是否已经打开、驱动是否启用接收、硬件 FIFO 大小和流控状态。

如果没有打开端口：

- 部分硬件仍会接收，但 FIFO 很快溢出。
- 溢出后的数据通常直接丢失。
- 驱动不保证永久保存数据。

如果端口已经打开但业务程序暂时不读取：

- 数据可能暂存在驱动队列。
- 队列或硬件 FIFO 满后仍会溢出。
- 硬件流控可以通知发送方暂停。

因此，“数据已经进入电脑”不等于“数据一定不会丢失”。

### 7.5 清空缓冲区

常见清理操作：

- `PurgeComm(PURGE_RXCLEAR)`：清除接收队列。
- `PurgeComm(PURGE_TXCLEAR)`：清除发送队列。
- `SerialPort.DiscardInBuffer()`：请求清空接收缓冲区。
- `SerialPort.DiscardOutBuffer()`：请求清空发送缓冲区。

清空接收缓冲区适合只关注打开之后的新数据。若连接建立前可能已经有关键响应，应根据协议决定是否清空。

### 7.6 超时

读取超时用于避免业务线程无限等待。应用可能关心：

- 首字节超时。
- 字符间隔超时。
- 整帧总超时。

虚拟驱动应同时处理等待中的读取取消，避免端口关闭或设备删除后残留请求。

## 8. 协议分帧

串口没有消息边界，只有字节流。常见分帧方法：

| 方法 | 示例 | 优点 | 风险 |
|---|---|---|---|
| 行分隔 | `PING\r\n` | 简单可读 | 正文不能随意包含 CRLF |
| 长度前缀 | `LEN + PAYLOAD` | 边界明确 | 需要处理长度上限 |
| 固定长度 | 每帧 16 字节 | 实现简单 | 不适合可变数据 |
| 帧头帧尾 | `AA 55 ... 0D 0A` | 易恢复同步 | 需处理正文转义 |
| 二进制协议 | Modbus RTU 等 | 紧凑高效 | 依赖 CRC 和超时 |

对于 UTF-8：

- `ReadExisting` 按字符串读取不适合作精确字节协议。
- 一个中文字符可能跨多次接收。
- 应先按字节完成分帧，再对完整帧进行 UTF-8 解码。

## 9. 物理串口和虚拟串口的区别

| 能力 | 真实串口 | 当前虚拟串口 |
|---|---|---|
| 电气 TXD/RXD | 有 | 无 |
| 硬件 UART FIFO | 有 | 无 |
| 真实线路时序 | 有 | 默认不模拟 |
| 波特率 | 决定实际传输速度 | 作为设备参数保存和查询 |
| 数据位/校验/停止位 | 影响帧同步 | 作为设备参数保存和查询 |
| RTS/CTS、XON/XOFF | 可控制真实发送 | 当前仅兼容部分 IOCTL，未模拟线路时序 |
| 接收缓存 | 硬件和驱动决定 | 固定环形缓冲区 |
| 数据注入 | 外部设备产生 | 控制接口写入驱动缓冲区 |
| 数据响应 | 外设响应 | 业务层规则匹配后注入 |

本项目当前串口参数由模拟器设备作为权威来源。业务端打开 COM 后应查询设备参数，不应假设打开时传入的默认值就是实际配置。

## 10. 当前模拟器的收发模型

```text
模拟器数据生成器
→ IOCTL_SIM_INJECT
→ 驱动 RingBuffer（65535 字节可用）
→ COM3 Read
→ 串口调试助手/业务测试端

串口调试助手/业务测试端 Write
→ COM3
→ 驱动 BusinessRequests（65535 字节可用）
→ IOCTL_SIM_RECEIVE
→ RequestResponder 分帧和规则匹配
→ IOCTL_SIM_INJECT 自动回复
```

当前驱动有两块 65536 字节分配的环形缓冲区：

| 缓冲区 | 分配大小 | 有效容量 | 数据方向 |
|---|---:|---:|---|
| `RingBuffer` | 65536 | 65535 | 模拟器 → 业务端 |
| `BusinessRequests` | 65536 | 65535 | 业务端 → 模拟器 |

环形缓冲区保留 1 字节区分空和满。模拟器注入前检查剩余空间；空间不足时返回溢出错误，不静默覆盖旧数据。

缓冲区中的重要数据在以下情况会丢失：

- 删除虚拟设备。
- 重启电脑。
- 驱动被重新加载。
- 主动执行接收清理。

## 11. 常见问题与排查

### 11.1 提示 COM 端口被占用

标准 COM 设备通常只允许一个业务客户端独占打开。排查：

1. 串口助手是否已经打开同一端口。
2. 是否启动了两个串口助手实例。
3. 是否存在残留业务进程。
4. 模拟器注入目标是否与实际打开的 COM 一致。

模拟器使用独立控制接口，正常情况下不会占用 COM 业务句柄。

### 11.2 能打开端口但收不到数据

依次检查：

1. 模拟器显示的注入目标与串口助手端口是否一致。
2. 模拟器是否显示持续 TX 注入。
3. `BytesToRead` 是否大于 0。
4. 业务端是否依赖 `DataReceived`；事件不触发时可使用轮询。
5. 是否已打开正确编码和显示模式。
6. 是否调用了 `DiscardInBuffer` 误清除刚到达的数据。
7. 是否被流控状态阻止。

### 11.3 第一次读取数据很多

通常是打开端口前积压的数据。可通过消息时间戳、计数器或序列号确认发送时间。

### 11.4 数据乱码

真实串口常见原因：

- 波特率不一致。
- 数据位、校验位或停止位不一致。
- 使用了错误的文本编码。
- 二进制数据被当作 UTF-8 或 ASCII 显示。
- 线路电平不兼容。

虚拟串口数据本身按字节传递，但仍应按完整帧进行正确编码。

### 11.5 数据截断或丢失

检查：

- 是否把一次读取误认为完整报文。
- 接收缓冲区是否溢出。
- 业务程序是否读取过慢。
- 是否发生流控暂停。
- 设备是否被拔出。
- 是否调用了清空缓冲区。

## 12. 推荐设计原则

1. 明确串口参数的所有权，避免双方互相覆盖。
2. 业务程序打开端口后查询实际参数。
3. 串口协议必须定义分帧，不依赖读取边界。
4. 重要协议使用长度、序号和 CRC。
5. 接收事件只作为通知，读取和分帧独立实现。
6. 为缓存溢出定义明确策略，不静默丢弃。
7. 长时间未读取时考虑流控或限制发送速率。
8. 记录端口名、字节数、时间戳和错误码。
9. 区分真实串口时序和虚拟串口元数据。
10. 对取消、关闭、设备删除和重启进行测试。
